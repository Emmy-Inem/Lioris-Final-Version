# SQL to run by hand (Supabase Dashboard -> SQL Editor)

Generated by `tools/build-manual-sql.sh` from `supabase/migrations/` (do not edit these files; edit the migrations and
rebuild). `tools/sql-harness/manual-apply.mjs` proves on every CI run that `02_apply_all.sql` applies as one paste,
is safe to run twice, and that the "stop if an earlier part is missing" guard works.

Run them **in this order**, each as one paste-and-Run:

| # | File | What it does | Changes data? |
|---|------|--------------|---------------|
| 1 | `01_diagnostics_before.sql` | Reads the live database and reports which audit findings are present. Save the result grid. | No (read-only) |
| 2 | `02_apply_all.sql` | Applies every migration from 20261028 to the latest (16 parts: the last two add the age/guardian rules, server-sent event reminders and signed-out page views), in order, each in its own transaction, with a lock timeout and a chain guard. | Yes - schema, policies, functions, a few one-off backfills |
| 3 | `03_verify_after.sql` | The same report plus: which parts are recorded as applied, which are missing (expect 0), and which security-definer functions anonymous callers can still run (expect exactly `check_username_available` and `record_public_page_view`). | No |

## Before step 2
1. **Off-peak.** Some parts take short locks on `profiles` and chat tables. The script sets `lock_timeout = 8s`: if the
   database is busy it fails fast instead of freezing the app. Just run the whole file again.
2. **Deploy the edge functions first** (they fall back where noted, but some need the new SQL; deploy again after step 2):
   `login-with-username`, `admin-create-user`, `admin-force-signout`, `admin-review-giving-campaign`,
   `admin-review-paid-event`, `delete-my-account`, `send-push`, `purge-expired-verification-documents`
   (`supabase functions deploy <name>`). `admin-review-giving-campaign` and `admin-review-paid-event` must be deployed
   together with step 2 (their SQL function signatures changed).
3. **Admin tiers.** Every platform-wide administrator needs `admin_role = 'super_admin'` (the diagnostics list the admins).
4. If a part fails: read the error, fix the cause, and run the whole file again. Parts already recorded in
   `public._manual_migration_log` finish instantly, and no part runs while an earlier one is missing.

## After step 3
- Create the Vault secrets `lioris_project_url` and `lioris_cron_secret` (same value as the `CRON_SECRET` function secret)
  and run `select public.schedule_verification_document_purge();` so the 30-day ID-document purge is scheduled.
- Ship the app/web build.

## Optional: require two-factor for admins (off by default)
Only when every admin has enrolled (the last diagnostic row counts them):

```sql
INSERT INTO public.platform_settings (key, value, description)
VALUES ('admin_mfa_required', '{"enabled": true}', 'Require AAL2 for enrolled admins')
ON CONFLICT (key) DO UPDATE SET value = EXCLUDED.value;
```
Undo: `UPDATE public.platform_settings SET value = '{"enabled": false}' WHERE key = 'admin_mfa_required';`

## Step 4: post-setup (after 02_apply_all.sql)

Run `04_post_setup.sql` once, then again whenever its report says ACTION NEEDED. It enables pg_cron / pg_net / Vault when
they are off, creates the Vault secrets for the ID-document purge (the cron secret is random and is created only if it does
not exist), schedules every background job that is missing (reminders and retention clean-ups), promotes the administrators
whose e-mails you put in the list at the top of the file, and prints a report (item, status, detail).

If the report says `lioris_cron_secret` was just created, copy its value (query at the bottom of the file) and set it as the
edge-function secret `CRON_SECRET`; the purge function rejects the job until the two match.

## Edge functions

`scripts/deploy-supabase.sh` deploys every function (the verify-jwt policy is read from `supabase/config.toml`, so
`login-with-username`, which is called before sign-in, is deployed with the JWT check off), lists missing secret names and
smoke-tests the functions. The workflow `.github/workflows/deploy-edge-functions.yml` runs it for you when function code
changes on `main`, or by hand from the Actions tab. It stays idle until the repository secret `SUPABASE_ACCESS_TOKEN` exists
(Supabase dashboard > Account > Access Tokens). Function secrets (`CRON_SECRET`, `GEMINI_API_KEY`, ...) are set in Supabase
under Edge Functions > Secrets.
